# antithrow core API audit — strengths

> Part of the [API audit](../API_AUDIT.md). What the audit found to be genuinely well-designed — each entry was observed empirically by a dimension auditor.
> Findings are grouped by audit dimension. Repro scripts referenced in evidence lived in the session scratchpad (ephemeral); all key observed output is quoted inline. The full untruncated register is in [findings.json](./findings.json).

- **(ok-runtime)** The `Pending` absorption story mostly works out: `ok.map(() => pendingErr)` produces `Pending<Settled<number, "inner">, string>` and the type genuinely says the value is a `Settled` — the compiler does not hide the nesting. Calling `.flatten()` on it then recovers the inner `Err` correctly at runtime (`map(->Pending<Err>).flatten() settled ctor => Err`, `isErr => true`), so the escape hatch composes across the async boundary.
- **(ok-runtime)** The phantom-`E` identity casts in `mapErr`/`orElse`/`flatten` are genuinely sound as re-typings — `Ok` carries no error payload, so there is nothing to leak. The `// SAFETY:` comments explaining each one are the right engineering practice and made auditing them fast.
- **(ok-runtime)** `Ok`'s short-circuit methods are rigorously lazy: `mapErr`, `orElse` and `unwrapOrElse` never invoke their callbacks on an `Ok` (verified: 0 invocations), so passing an expensive or throwing recovery function costs nothing. That is easy to get wrong and it is right here.
- **(ok-runtime)** `Ok` is deliberately NOT `PromiseLike`, which means `Promise.resolve(this)` inside `settle()` cannot be absorbed and `await ok` returns the `Ok` itself rather than silently unwrapping. Given how much of the design rests on thenable detection, keeping the settled classes non-thenable is the correct call.
- **(ok-runtime)** The `NoInfer<U>` on `mapOr`'s `defaultValue` and the `NonThenable<U>` / `SameResolved<A, B>` helpers in types.ts show real care about inference direction — the overload sets steer sync callbacks into sync signatures instead of collapsing everything into `T | Promise<T>`, which is the usual failure mode for libraries of this shape.
- **(ok-runtime)** `util.inspect`/`console.log` output is clean and unambiguous out of the box (`Ok { value: 42 }`, `Err { error: 42 }`) purely from good class naming and a single public field — debugging sessions read well even without a custom inspector.
- **(err-runtime)** The `Err` fast path is allocation-free and provably side-effect-free: `map`, `andThen`, `and` and `flatten` all return `this` (verified `B1`-`B4` all `true`), and the callbacks are never invoked (`B6 map/andThen callbacks invoked count = 0`, and `P8 map fn throw (never called on Err) OK`). Chaining ten combinators onto an error costs zero objects and zero calls — that also gives React-style reference stability for free.
- **(err-runtime)** `Err`'s concrete return types are strictly more precise than the abstract base signatures and they are correct: `andThen`/`and` return `Err<InferOk<R>, E>` (correctly dropping `InferErr<R>`, since the callback never runs), `or`/`orElse` return `R` exactly, and `FlattenErr` correctly preserves the outer `E` while flattening the phantom `T` — confirmed by declaration emission: `e.andThen(() => new Ok<boolean, Date>(true))` ⇒ `Err<boolean, string>`, `e.or(new Ok<number, boolean>(1))` ⇒ `Ok<number, boolean>`, `Err<Ok<number,string>, boolean>.flatten()` ⇒ `Err<number, string | boolean>`.
- **(err-runtime)** `mapOr` is exactly right on the error path: it returns the default without touching the mapper, verified by the evaluation log `D1 mapOr result = 99 | evaluation log = [ "default-arg-evaluated" ]` — only the (necessarily eager) argument was evaluated, the mapper never ran. `mapOrElse` likewise calls only `defaultFn` (`D2 … order = [ "defaultFn" ]`).
- **(err-runtime)** `settle()` is correct and subclass-transparent: it resolves to the very same instance (`H2 settle resolves to same instance: true`) and preserves subclasses (`M3b settle preserves subclass: true`), so `await result.settle()` is a genuine no-op on the settled path.
- **(err-runtime)** `isThenable` correctly refuses to assimilate a non-callable `then` — `C11 {then:42} ->  Err` — which rules out the most common accidental false positive (a plain data object with a `then` field).
- **(err-runtime)** `orElse` handles the async-recovery case cleanly when given a `Pending`: `new Err("e").orElse(() => Result.try(async () => 0))` returns a well-formed `Pending` that settles to `Ok 0`, with no assimilation weirdness — this is the right primitive, it just needs to be advertised.
- **(err-runtime)** The compiler correctly rejects the two most tempting mistakes on this surface: `new Err()` (`TS2554: Expected 1 arguments, but got 0`) and `orElse(async () => new Ok(0))` — both `@ts-expect-error` markers were consumed, so the guardrails genuinely fire rather than merely being intended.
- **(err-runtime)** `UnwrapError` keeps a live reference to the originating result (`F4 ue.result is the Err instance: true`) and its stack is rooted exactly at the failing call (`at unwrap (/home/user/antithrow/packages/antithrow/src/err.ts:99:13)` followed immediately by the user frame), so once you know to look at `.result` the debugging experience is genuinely good.
- **(err-runtime)** The iterator's cleanup contract is honoured: `return()` after the first yield produces `{ value: undefined, done: true }` and subsequent `next()` calls stay done — which is precisely why `Result.do`'s `iter.return?.()` short-circuit works correctly (`K1 Result.do short circuit: Err bad`).
- **(pending-runtime)** The SAFETY casts in `Pending.map`/`mapErr` (pending.ts:52,59) are actually accurate, not hand-waves. `Pending<number,string>.map(() => somePending)` is declared `Pending<Settled<string,string>, string>` and at runtime you get exactly an `Ok` wrapping an `Ok` — one level of nesting, precisely as typed. Verified by `tsc --noErrorTruncation ... 08-reveal.ts` printing `Type 'Pending<Settled<string, string>, string>'` and `bun 01-basics.ts` printing `9. Pending.map(fn->Pending) awaited: Ok value: {"value":"deep"} value is Pending? false value is Ok? true`. `map(() => new Ok(...))` gives the same one-level nesting (`Pending<Ok<string,string>, string>`), so the flattening depth is consistent between Result-returning and Pending-returning callbacks.
- **(pending-runtime)** `flatten()` composes correctly through the async boundary: `Pending<Ok<Pending<Ok(5)>>>.flatten()` awaits to `Ok(5)` (`bun 14-flatten.ts` -> `1. ... -> Ok {"value":5}`), while an unflattened await correctly leaves the inner `Pending` intact (`3. without flatten, inner value stays a Pending: true`). The `map` (nests) vs `andThen` (flattens) distinction also holds exactly on the Pending path (`4. map(->Pending) leaves an Ok<Ok<'x'>>` / `4. andThen(->Pending) fully flattens`).
- **(pending-runtime)** The inner promise is shared correctly: multiple awaits of one `Pending` return the *identical* `Settled` instance, multiple `.then` calls return distinct promises with equal values, and branching one `Pending` into two independent chains evaluates the source exactly once (`bun 01-basics.ts` -> `3. two awaits give identical Settled instance: true true`; `bun 10-misc.ts` -> `5. source promise evaluated once: 1 branches: 2 11`). `settle()` is a true zero-allocation alias (`settle() === settle() === .promise: true true`).
- **(pending-runtime)** The constructor is properly type-guarded against a non-Settled payload — `new Pending<number, string>(Promise.resolve(5))` is a compile error (confirmed via a consumed `@ts-expect-error` in 07-typecheck.ts) — and `Pending` composes with the standard promise combinators with exactly right types: `Promise.all([p, p])` is `[Settled<number,string>, Settled<number,string>]`, `Promise.race([p])` is `Settled<number,string>`, `Promise.allSettled([p])` is `[PromiseSettledResult<Settled<number,string>>]`. All asserted with `Equal`/`Expect` and clean at `tsc` exit 0.
- **(pending-runtime)** The `Result.do` integration is solid on the async path: `yield* pending` works, fail-fast short-circuits on `Err`, and `iter.return()` genuinely runs the generator's `finally` block (`bun 06-asynciter.ts` -> `E. Result.do with yield* Pending: {"value":3}` and `F. fail-fast result: {"error":"bad"} finally ran: true`). The type system also correctly *rejects* the analogous mistake in a synchronous generator — `yield* p` inside `Result.do(function* ...)` is a compile error (consumed `@ts-expect-error` in 13-typecheck2.ts) — catching at build time what would otherwise be `TypeError: yield* new Pending is not a function` at runtime.
- **(pending-runtime)** `then` is a faithful `PromiseLike` implementation in the details that are easy to get wrong: zero arguments and explicit `null, null` handlers both pass through to the `Settled` value, a throwing `onfulfilled` rejects the derived promise, and `onrejected` receives the raw reason with the union type `PromiseLike<A | B>` inferred correctly (`bun 10-misc.ts` -> `1. p.then() => {"value":1}`, `1. p.then(null, null) => {"value":1}`, `2. then(onfulfilled that throws) rejects: in onfulfilled`).
- **(pending-runtime)** `unwrap()`/`unwrapErr()` on the wrong branch reject with a real `UnwrapError` carrying the originating result, exactly as the docs promise: `bun 03-poisoned.ts` -> `unwrap() on Pending-of-Err rejects with: UnwrapError true {"error":"failed"}` (`e instanceof UnwrapError` is `true` and `e.result` is the `Err`). The error identity survives the async boundary intact.
- **(pending-runtime)** `new Pending(anotherPending)` — which the type system permits, since `Pending<T,E>` structurally *is* `PromiseLike<Settled<T,E>>` — behaves sensibly rather than breaking: it awaits to the inner `Settled` and `.map` on it works normally (`bun 01-basics.ts` -> `5b. new Pending(pending) awaits to: Ok {"value":99}` / `5b. .map on double-wrapped works: 100`). A `Pending` stored *inside* an `Ok` is likewise left untouched by `await` (`5. await nested -> ctor: Ok value is Pending: true`).
- **(constructors)** E defaults to `unknown`, not `any` or `never`, in both factories — the safest possible default. Verified by reveal.ts: `Result.try(() => 42)` is `Settled<number, unknown>` and `Result.fromPromise(Promise.resolve(42))` is `Pending<number, unknown>`. Many Result libraries default to `Error` and lie from the first line.
- **(constructors)** The three-way overload dispatch is genuinely precise for the common shapes, and the `NonThenable<T>` trick to keep `T | Promise<T>` out of the sync-only signature is clever and works. typecheck.ts asserts and tsc confirms: `() => 42` → `Settled<number, unknown>`, `async () => 42` → `Pending<number, unknown>`, `() => number | Promise<number>` → `Result<number, unknown>`. Getting a sync/async-polymorphic factory to return three different static shapes without any cast at the call site is not easy.
- **(constructors)** Contextual typing flows the declaring function's return type into E, so `function f(): Result<number, string> { return Result.try(() => 42); }` compiles with no type arguments (typecheck2.ts, tsc exit 0). Ergonomically excellent — the caveat is only that nothing validates it (ok-2).
- **(constructors)** `fromPromise` attaches its handlers eagerly, so a rejecting promise never produces an unhandled-rejection warning even if the Pending is not awaited for many ticks. runtime2.ts H1 confirms: after a 10ms delay the result still settles cleanly to `Err(Error: x)` with no process-level warning.
- **(constructors)** `Pending` is re-awaitable and the underlying work runs exactly once: runtime2.ts H2 awaits the same `Result.try(async ...)` three times and reports `fn calls=1`. Wrapping the promise rather than the thunk is the right call here.
- **(constructors)** Non-Error throws are preserved faithfully rather than being coerced into an `Error`: runtime2.ts E4 shows `throw undefined`, `throw null` and `throw 0` yield `Err(undefined)`, `Err(null)` and `Err(0)` respectively, with the exact value intact. Several competing libraries stringify or wrap these and lose information.
- **(constructors)** `Result.try` is defensive about its own argument — `Result.try(undefined as any)` returns `Err(TypeError: fn is not a function)` rather than throwing (runtime2.ts G5), and an object with a `then` getter that throws also yields an `Err` (runtime3.ts G6).
- **(do-notation)** The classic generator hazard is handled correctly: `resultDo` captures `next.value` *before* calling `iter.return()`, so a `finally { return somethingElse }` cannot swallow or replace the short-circuit `Err`. Verified — `PRAISE-1: Err("kept")` in 10-findings-repro.ts, where the finally returns 999 and the Err survives intact. Many hand-rolled do-notation implementations get this wrong.
- **(do-notation)** The async path awaits `iter.return()` before resolving, so asynchronous cleanup genuinely completes before the caller observes the result — `PRAISE-2: Err("e") ["async-cleanup-done"]` with a 10 ms `setTimeout` inside the `finally`. The ordering guarantee is stronger than the docs claim.
- **(do-notation)** Only one `iter.next()` call is needed for the entire block, because `Ok`'s iterator yields nothing and `Pending`'s async iterator yields only on failure. That makes the implementation 25 lines and O(1) in driver overhead; measured cost is linear and cheap — 100,000 `yield* new Ok(...)` steps in ~26-31 ms, and short-circuiting out of a 100,000-iteration Err loop in 0.08 ms.
- **(do-notation)** `yield*` composes with user-written helper generators for free: `function* validate(n) { if (n < 0) yield* new Err("negative"); return n * 2 }` can be `yield*`ed from a `do` block and its error type flows into the union automatically (`AF ok -> Ok(8)`, `AF err -> Err("negative")`). This is a genuinely nice emergent property of delegating rather than driving.
- **(do-notation)** Error-union inference is exact, including across heterogeneous Err types and across `Settled`/`Result` unions: a block yielding `Err<never,"a">` and `Err<never,"b">` infers `Settled<number, "a" | "b">`, and `yield*` over a full `Result<number, "r">` union in an async generator infers `Pending<number, "r">` — the async iterator/sync iterator fallback works at both the type and runtime level for all four Ok/Err/Pending-Ok/Pending-Err cases.
- **(do-notation)** The four-overload table in the docs matches the implementation exactly, including the subtle `Generator<never, T, void> -> Ok<T, never>` case that lets a yield-free block keep an uninhabited error channel.
- **(do-notation)** `Ok`, `Err` and `Pending` instances are safely reusable across and within `do` blocks, because `[Symbol.iterator]`/`[Symbol.asyncIterator]` mint a fresh generator per call and `Pending` memoises a single promise — yielding the same `Pending` twice resolves twice from one underlying promise (`AD Ok(18)`).
- **(types-overloads)** The sync/async split on the common path is genuinely honest and I could not break it: `ok.map(x => x*2)` is exactly `Ok<number,string>`, `ok.map(async x => x*2)` is exactly `Pending<number,string>`, `err.map(async ...)` correctly stays `Err<number,string>` (it does NOT fabricate a Pending, because the callback never runs), and `res.map(async ...)` is exactly `Err<number,string> | Pending<number,string>`. All four match `instanceof` at runtime (assertions.ts A1-A7 compile clean; `bun runtime1.ts` prints ok=Pending / err=Err / pen=Pending for the async case).
- **(types-overloads)** `mapOrElse` with mixed branches is the sharpest piece of typing in the package. `ok.mapOrElse(_e => "sync", async _x => "async")` is typed exactly `PromiseLike<string>` and `err.mapOrElse(...)` on the same call is typed exactly `string` — each class reports which branch IT will actually take, and the runtime agrees (`bun runtime1.ts`: "ok -> runtime: object true" / "err -> runtime: string \"sync\"", and the reverse for async-default/sync-map). The `SameResolved<A,B>` helper is a clean way to express "same after await" and it does reject genuinely mismatched branches on all four receivers.
- **(types-overloads)** `Ok.map` with a `string | Promise<string>` callback distributes to exactly `Ok<string,string> | Pending<string,string>` — the union return type is faithfully reflected in the union result type, and the runtime picks the matching arm per call (`bun runtime1.ts`: ok(2).map(un) -> Ok, ok(3).map(un) -> Pending). Very few Result libraries model this at all.
- **(types-overloads)** The impossible-side unwraps are typed `never` rather than `T`: `err.unwrap()` is `never` and `ok.unwrapErr()` is `never`, so dead code after them is visible to the checker, and on the union they collapse cleanly to `number | PromiseLike<number>` / `string | PromiseLike<string>`.
- **(types-overloads)** `Ok.unwrapOrElse(async () => 0)` is typed `number`, not `PromiseLike<number>` — the library correctly notices that an `Ok` never invokes the fallback and so never becomes async. Runtime confirms (`number 1`). The same care shows in `Err.mapOr(0, async x => x*2)` typing as `number`.
- **(types-overloads)** `orElse` narrows the whole union cleanly: `res.orElse(recover)` on `Result<number,string>` with a `(e: string) => Result<number, boolean>` gives exactly `Result<number, boolean>` — a single tidy type, no leftover arms. This is the behaviour `or` should have had.
- **(types-overloads)** `settle()` collapses correctly across the union — `PromiseLike<Ok<...>>` on Ok, `PromiseLike<Err<...>>` on Err, and `PromiseLike<Settled<number,string>>` on the union (union reduction works because the classes are declared covariant with `out T, out E`). The explicit variance annotations are a good call and they do real work here.
- **(types-overloads)** Heterogeneous chains stay honest end to end: `new Ok<number,string>(2).map(x => x+1).map(async x => x*10).andThen(x => new Ok<string,boolean>(String(x))).mapErr(String)` types as `Ok -> Pending -> Pending -> Pending` and `bun unsound2.ts` prints exactly `Ok Pending Pending Pending`, settling to `Ok {"value":"30"}`. Once a chain goes async it stays async in both the type system and the runtime, with no drift.
- **(types-overloads)** `andThen`/`and` get the error algebra right per class: `Ok.andThen` passes `R` through verbatim (dropping its own unreachable `E`), `Err.andThen` keeps `E` and only borrows `InferOk<R>`, and `Pending.andThen` correctly unions to `E | InferErr<R>` because a Pending really can settle either way.
- **(types-guards-variance)** Narrowing through the three guards is complete and correct on the happy path: after `isOk()` false and `isErr()` false the union really does narrow to `Pending<T,E>`, `!r.isPending()` gives exactly `Ok<T,E> | Err<T,E>`, `.error` is correctly rejected on the non-Ok branch, and a fourth `const _: never = r` compiles — full exhaustiveness without a discriminant field (01-narrowing.ts, 10-exhaustive.ts, both tsc exit 0).
- **(types-guards-variance)** Three independent narrowing mechanisms give identical results: the `is*()` methods, `instanceof Ok/Err/Pending`, and `"value" in r` / `"error" in r` / `"then" in r` all narrow to the same types, including in the negative branches and for exhaustiveness. That parity is unusual and means users' instincts all work (01-narrowing.ts, 11-generic-and-in.ts).
- **(types-guards-variance)** The guards are plain methods returning constants rather than `instanceof` checks, so they survive the duplicate-package hazard that breaks `instanceof`. Demonstrated with two live copies of the library: `same class object? false`, `fromDist instanceof OkSrc: false`, but `fromDist.isOk(): true` (16-dual-copy.ts).
- **(types-guards-variance)** The `out T` / `out E` annotations are doing real work in the right direction: they *reject* the bivariance TypeScript would otherwise permit on phantom parameters. `Ok<number,string>` is not assignable to `Ok<number,boolean>`, `Err<never,string>` not to `Err<never,number>`, `Pending<number,string>` not to `Pending<number,boolean>`, and `Ok<Animal,never>` not to `Ok<Dog,never>` — all verified as errors (04-variance.ts).
- **(types-guards-variance)** Covariance makes annotation-free code flow correctly: `b ? new Ok(1) : new Err("e")` infers `Ok<number,never> | Err<never,string>` and assigns cleanly to both `Result<number,string>` and `Settled<number,string>` with no casts and no explicit type arguments (12-inference-flow.ts).
- **(types-guards-variance)** The phantom parameters are not exposed as phantom *data*: a narrowed `Err<number,string>` has no `.value` property and a narrowed `Ok<number,string>` has no `.error` property (both rejected), while `Err#unwrap()` and `Ok#unwrapErr()` are honestly typed `never` (14-phantom.ts).
- **(types-guards-variance)** Inferred type predicates (TS 5.5+) propagate through the guards, so the common cases just work with no hand-written predicate: `results.filter(r => r.isOk())` yields `Ok<number,string>[]`, `.filter(r => r.isErr())` yields `Err[]`, `.filter(r => r.isPending())` yields `Pending[]`, `.find(...)` yields `Ok | undefined`, and `.every(r => r.isOk())` narrows the array itself (03-filter.ts, 12-inference-flow.ts).
- **(types-guards-variance)** `Settled<T,E>` is assignable to `Result<T,E>` and `Result<T,E>` is correctly *not* assignable to `Settled<T,E>`, so the settled/pending distinction is enforced in the direction that matters (04-variance.ts).
- **(flatten)** FlattenOk preserving the inner *variant class* is strictly more precise than both Rust's `Result::flatten` and this library's own legacy `flatten` (which both return the full `Result<U, E|F>` union). `new Ok(new Ok(42)).flatten()` is `Ok<number, never>` and `Ok<Err<never,string>, E>.flatten()` is `Err<never, string|E>` — no needless re-narrowing at the call site. Verified: reveal2.ts(29,7) 'Ok<number, never>'.
- **(flatten)** Unioning the two error types as `E | F` is the right TypeScript adaptation of Rust, whose `Result::flatten` requires both error types to be *identical*. The documented headline case is exactly right: `Result<Result<number,string>, boolean>.flatten()` is precisely `Result<number, string | boolean>` (reveal2.ts(24,7): 'Pending<number, string|boolean> | Err<number, string|boolean> | Ok<number, string|boolean>'), matching the JSDoc example at base.ts:176-181.
- **(flatten)** flatten is idempotent-safe on over-application: triple-flattening a doubly-nested value both typechecks and behaves. `Ok<Ok<Ok<number,never>,never>,never>` flattens to `Ok<Ok<number,never>,never>` then `Ok<number,never>` and a third call is a stable `Ok<number,never>` (reveal4.ts lines 29/30/32), with runtime agreeing (runtime1.ts case 7).
- **(flatten)** The deferred conditional types stay usable behind generics — `function flattenAll<T, E>(rs: Result<Result<T, E>, E>[]): Result<T, E>[] { return rs.map(r => r.flatten()); }` and `function genericFlatten<T, E>(r: Ok<T, E>): Result<unknown, unknown> { return r.flatten(); }` both compile with no assertions (reveal4.ts, no diagnostics on those lines). Conditional-type-heavy APIs frequently fail this test.
- **(flatten)** Pending.flatten() handles every settled shape correctly, including the awkward ones: inner Err short-circuits (runtime1.ts 8c/8d), a raw `Promise` payload is correctly NOT mistaken for a Result and survives as a Promise inside the Ok (8f), and nested Pending chains collapse to the exact depth the type predicts (8b, 8e, runtime3.ts case 4/5).
- **(flatten)** Every `as unknown as` cast in the three flatten implementations carries an explicit `// SAFETY:` comment explaining the invariant (ok.ts:106, err.ts:94, and the assimilation notes at pending.ts:52/59). Two of those invariants turn out to be conditional rather than absolute (findings ok-1/ok-2), but the practice of writing them down is what made the gap findable.
- **(api-completeness)** `await` on a `Result` union collapses to exactly `Settled<T, E>` with no helper call — verified `Expect<Equal<Awaited<Result<number,string>>, Settled<number,string>>>` passes (19-praise-and-merge.ts, TSC EXIT=0). This is the payoff of making `Pending` a member of the union rather than a parallel type, and it is genuinely nicer than neverthrow's `ResultAsync`, where you must remember which type you are holding. `Promise.all` over a mixed `Result[]` also happens to work correctly as a settle-all (02-combine.ts), because `Ok`/`Err` are non-thenable and pass through.
- **(api-completeness)** `Result.try` preserves synchronicity in the type rather than pessimistically returning the full union: `Result.try(() => 1)` is `Settled<number, unknown>` and `Result.try(async () => 1)` is `Pending<number, unknown>` (19-praise-and-merge.ts). The `NonThenable<T>` overload trick that achieves this is careful work, and it means the three-state model does not tax code that never goes async.
- **(api-completeness)** The unannotated default error type is `unknown`, not `any` — `Result.try(() => JSON.parse("{}") as {a:number})` reveals as `Settled<{a:number}, unknown>` (14b.ts). The default is the safe one; the hole in ok-1 only opens when a user explicitly asserts otherwise.
- **(api-completeness)** `Result.do` (neverthrow's `safeTry`) is well-typed and precise about reachability: yielding a statically-known `Ok<number, "E1">` contributes nothing to the error channel (because `Ok[Symbol.iterator]` is `Generator<never, T, void>`), while yielding a real `Err` or a `Result` union contributes its error type. `Result.do` over a `Result<number, string>[]` correctly infers `Pending<number[], string>`, and the sync/async generator overloads keep sync flows sync (03-combine-types.ts, 19-praise-and-merge.ts). Getting the `never`-yield encoding right is the hard part of this pattern and it is done correctly.
- **(api-completeness)** `UnwrapError` carries the offending result as a typed `Settled<unknown, unknown>` property rather than only a string, so a catcher can re-inspect the failure programmatically (19-praise-and-merge.ts, 12-serialization.ts). Most libraries throw a bare `Error` here.
- **(api-completeness)** `Result` is a merged type alias and value under one name, so a single `import { Result }` serves both `Result<T, E>` annotations and `Result.try(...)` calls — no separate namespace import, which is a small thing that shows up on every file in a codebase.
- **(api-completeness)** The `SafetyE`/`SameResolved`/`FlattenThenable` type helpers and the `// SAFETY:` comments on every internal cast show real discipline about where the unchecked assertions live. The casts that exist are localized, annotated, and each one is defensible (casting an uninhabited `never` channel).
- **(docs-accuracy)** Every runtime-value comment in base.ts's @example blocks is correct — all 15 checked (`// 10`, `// 0`, `// 5`, `// "failed"`, `Ok(42)`, `Error("failed")`, etc.) matched observed output exactly on the first run (01-base-runtime.ts). The value-level documentation is genuinely trustworthy; only the type-level annotations drift.
- **(docs-accuracy)** The `@throws Errors thrown by \`fn\` are not caught.` claim is accurate for every method that carries it, and holds for the async case too: `Ok.map(async () => { throw ... })` produces a `Pending` whose promise rejects rather than an `Err` (13-throws-and-maporelse.ts). This is the library's most consequential design decision and the docs state it consistently in base.ts, the README warning block, result.ts's Result.do JSDoc, and reference/result.md — four independent places, all agreeing.
- **(docs-accuracy)** errors.ts's UnwrapError example is exactly right, including the type claim `error.result; // Settled<unknown, unknown>` which passes a strict `Equal` assertion (06-other-jsdoc.ts). The message strings quoted in unwrap-error.md L34-35 also match verbatim, and `pending.unwrap()` on an Err branch really does reject with an `UnwrapError` as L36 promises.
